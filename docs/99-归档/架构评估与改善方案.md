# 生产化高并发架构评估与改善方案

> 版本：v1.0 · 2026-08-17
> 背景：工单台功能已上线（P0 快速落单 + P1 分页/布局），考虑实际投产后使用者变多、存在高并发可能，对当前架构进行风险盘点并给出分阶段改善方案。
> 结论：阶段 1（单机高并发加固）为投产前必做项，见下文「三、分阶段方案」。

---

## 一、现状关键事实（已核实）

| 项 | 现状 |
|---|---|
| 后端 | FastAPI 同步端点（`def` 非 `async def`），uvicorn 单进程单 worker，线程池默认 40 |
| 数据库 | SQLite（WAL 已开），单文件 `data/app.db`，全量数据一张库 |
| Agent 执行 | `POST /run` **同步阻塞**：整个 Agent 循环（40–200 秒）在 HTTP 请求线程内跑完才返回 |
| 实时通道 | WS（`/api/tickets/{id}/ws`）+ 前端 1s 轮询双通道 |
| 鉴权 | PBKDF2 密码哈希 ✓ + DB sessions 表 + `X-Auth-Token`（无 JWT / 无刷新续期 / 无主动撤销） |
| 前端 | Next.js **客户端渲染**（首屏 JS 执行渲染），nginx 静态代理 |
| 网关 | 单 nginx，`proxy_read_timeout 300s`，WS 升级已配置 |
| 状态机 | `transition()` 为「读状态 → 校验 → 更新」非原子操作，无乐观锁 |

## 二、高并发风险点（按严重程度排序）

### 🔴 风险 1：Agent 同步执行占满线程池（最致命）
- 一次 `POST /run` 持有 HTTP 线程 40–200 秒（流水线 + Agent 循环全同步）。
- FastAPI 同步端点跑在线程池（默认 40 线程）：**40 个用户同时建单 = 线程池全占满** → 登录、列表、轮询等轻请求全部排队，系统整体"卡死"。
- 现有"快速落单"只解决前端感知（create 秒回），**run 的线程占用没有变**。

### 🔴 风险 2：SQLite 写锁串行化
- 多工单并行执行时 `ticket_events` / `state_transition` / trace 高频写入；WAL 只改善读写并发，**写仍是单写锁**。
- 高并发下 `database is locked` 可能常态化 → 状态机转移失败 → 工单流程中断。
- 单文件 DB 无法横向扩展（多副本争锁）。

### 🟠 风险 3：状态机无并发防护（竞态）
- 同一工单被并发触发两次 run（或 run 与取消/审批同时到达）→ 双跑流水线、双写事件、状态错乱。
- 前端有 busy 防抖，**后端无防护**。

### 🟠 风险 4：1s 轮询放大后端压力
- 每个活跃工单每秒 2 请求（getTicket + getConversation）+ 每 10s 列表。
- 100 在线用户同时开工单 ≈ **300 req/s 纯轮询流量**，且多数结果无变化，浪费 DB 读。

### 🟠 风险 5：外部 LLM 依赖无保护
- OpenRouter 免费模型限流（429）→ 全部回落 Ollama 远程（更慢）→ 排队恶化。
- 无请求级并发信号量、无限流、无单请求超时兜底（httpx 默认 120s 硬编码）。

### 🟡 风险 6：会话无刷新续期、无主动撤销
- sessions 有 TTL，但前端不续期；到期后静默 401。

### 🟡 风险 7：单副本单点
- app/web/nginx 各 1 副本；nginx 挂了全站挂；无健康检查自动拉起。

### 🟡 风险 8：事件表无限增长
- `ticket_events` 全量保留、conversation 全量拉取；数据增长后轮询变慢。

## 三、分阶段改善方案

### 阶段 1：单机高并发加固（低成本，投产前必做）

| # | 措施 | 解决风险 | 改动量 | 效果 |
|---|---|---|---|---|
| 1 | **Agent 执行后台任务化**：`POST /run` 入队即返回（`{status:"queued"}`），Agent 循环由 in-process worker 线程池执行，事件照常写 DB + WS 推送 | 风险 1 | 后端 ~几十行，前端零改动（已有轮询/WS 兜底） | HTTP 线程不再被 Agent 占用；Agent 并发被 worker 池封顶（如 3~5），LLM/DB 压力可控 |
| 2 | **状态机乐观锁**：`UPDATE ... WHERE status=?` 条件更新，失败抛 409 | 风险 3 | 后端小改 | 杜绝双跑、状态错乱 |
| 3 | **SQLite 参数调优**：`busy_timeout=5000` + `synchronous=NORMAL`（WAL 下安全） | 风险 2 | 后端 2 行 | 减少 `database is locked` |
| 4 | **轮询降频 + 条件刷新**：1s → 2~3s，状态变化即时刷新、兜底拉长 | 风险 4 | 前端小改 | 轮询流量降 2~3 倍 |
| 5 | **LLM 并发信号量 + 超时**：`Semaphore(4)` + 单请求超时 60s，超时走降级链 | 风险 5 | 后端小改 | 防 LLM 雪崩 |

### 阶段 2：多副本可扩展（用户量级增长时）

| # | 措施 | 解决风险 | 说明 |
|---|---|---|---|
| 6 | 数据库升级 PostgreSQL | 风险 2、8 | daos 层从 sqlite3 裸 SQL 抽象成 DB-API 兼容层或迁移 SQLAlchemy；写并发提升数量级，支持多副本共享 |
| 7 | App 多副本 + nginx upstream 负载均衡 | 风险 7 | WS 广播需引入 Redis pub/sub 或改轮询为主（前端已有兜底） |
| 8 | 任务队列外置（Redis RQ / Celery） | 风险 1 的规模扩展 | Agent 执行从 in-process worker 升级为独立 worker 容器，支持横向扩容、断点重试、执行监控 |

### 阶段 3：生产级治理（正式对外前）

| # | 措施 | 解决风险 |
|---|---|---|
| 9 | JWT + 刷新令牌 + 登出撤销 | 风险 6 |
| 10 | 限流中间件（按用户/按接口） | 风险 5 的入口侧 |
| 11 | 可观测性：Prometheus 指标 + 日志聚合 + 告警 | 运维 |
| 12 | 事件表归档/分区，conversation 分页 | 风险 8 |
| 13 | 多副本部署（Compose 扩展 / K8s）+ 健康检查自愈 | 风险 7 |

## 四、优先级建议

- **投产前必须做**：阶段 1 的 1（后台任务化）、2（防竞态）、3（DB 调优）——决定高并发下"能用"。
- **用户量到百级**：阶段 1 的 4、5 + 阶段 2 的 6、7。
- **用户量到千级 / 正式对外**：阶段 2 的 8 + 阶段 3 全部。

其中**风险 1（后台任务化）收益最大**：改动集中在后端 run 入口，前端零改动，却能把并发能力从"~40 个同步工单"提升到"HTTP 无阻塞 + Agent 并发可控"。
