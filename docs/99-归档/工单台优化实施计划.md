- **版本**：v1.0
- **日期**：2026-08-16
- **范围**：工单台页面（`web/app/tickets/page.tsxx` + `web/app/globals.css` + 后端 `app/api/tickets.py` + `app/daos/tickets.py`）

## 0. 现状基线（改造前）

| 模块 | 现状 | 与需求的差距 |
|---|---|---|
| 布局 | `.ticket-layout` 为 `grid-template-columns: 300px 1fr`；`@media(max-width:900px)` 单列；列表卡片内联样式 | 左栏 300px 偏窄、内容紧凑；右栏 `1fr` 未按需压缩；响应式只有一档阈值 |
| 列表加载 | 后端 `daos.list_tickets(tenant_id, limit=50)` **全量一次性返回**（无 offset/分页）；前端 `listTickets()` 全量拉取，`filtered` 在**前端 useMemo 本地**做搜索/筛选 | 无分页接口、无分页状态管理；数据量大时渲染/加载卡顿；搜索/筛选与后端无联动 |
| 新建工单 | `POST /api/tickets` 同步串行执行 `relevance_check → rewrite_content → classify`（每次 LLM 往返数秒~数十秒）；前端 `submit()` `await createTicket(form)` 全程 `busy` 阻塞，按钮显示"校验中…"，**无分阶段反馈** | 用户在无反馈状态下长时间等待；不满足"点击即跳聊天页 + 流式展示全流程" |

> 关键：需求②与③的改造会**触及同一份列表渲染代码与建单链路**，故将两者解耦、错峰并联，详见排期。

## 1. 需求①：页面布局调整

### 1.1 设计目标
- 拓宽工单一览（左栏）适度宽度，提升信息密度可读性：**默认 300px → 380~420px（可拖拽可选，不做则固定 400px）**。
- 压缩右栏（聊天/工单内容栏）显示宽度，保证整体空间协调，避免左右失衡。
- 多档响应式断点（≥1280px / 900–1280px / <900px），窄屏自动降为单列，不破版。

### 1.2 实施内容
**前端 CSS（`web/app/globals.css`）—— 责任人：前端**
1. 调整 `.ticket-layout` 栅格：`grid-template-columns: minmax(380px, 420px) 1fr; gap: 20px;`
2. 重构卡片内部：标题区、元信息（状态徽标/意图/时间/归属人）、管理员"删除"按钮改为 CSS 定位，去除内联 `style`，统一到类名。
3. 响应式三档：
   - `≥1200px`：双列宽左栏（上面配置）
   - `≤1199px && ≥900px`：`grid-template-columns: 340px 1fr`
   - `≤899px`：单列 `1fr`，左栏 `max-height 240px`，右栏 `height calc(100vh - 320px)` 且 `min-height 440px`
4. 列表区 `overflow-y:auto` 滚动条美化（细滚动条），为分页（需求②）后的卡片展示预留视觉空间。

**验收标准（本模块）**
- 桌面端左栏 ≥380px、右栏对应收窄，无横向滚动条、无元素溢出。
- 在 1280 / 1024 / 768 / 375 四档视口下无布局错乱、无遮挡、按钮可点击。
- 删除按钮在 `@media` 各档均不遮挡标题/状态。

## 2. 需求②：分页功能开发

### 2.1 设计目标
- 将全量加载改为**服务端分页**，每页控制在 **20 条**（可配置），解决渲染/加载卡顿。
- 保留既有**搜索（ID/标题）与状态筛选（全部/待审批/处理中/已完成/失败）与分页的联动**：筛选与搜索改变时回到第 1 页并重新请求。
- 分页状态在前端集中管理（当前页、每页条数、总条数、总页数、加载态）。

### 2.2 技术方案（前后端分工）

**后端（`app/api/tickets.py` + `app/daos/tickets.py`）—— 责任人：后端**
1. `daos.list_tickets(tenant_id, *, limit=20, offset=0, requester_id=None, status=None, q=None)` 扩展：
   - 追加 `LIMIT ? OFFSET ?`
   - `status=None` 时不按状态过滤；否则按指定状态集合过滤（用于 Tab）。
   - `q` 对 `t.id`（数字匹配）或 `t.title`（LIKE，忽略大小写）过滤。
2. `daos.count_tickets(tenant_id, *, requester_id=None, status=None, q=None)`：返回满足条件的总条数（分页元数据）。
3. 接口适配：
   - `GET /api/tickets?page=1&page_size=20&status=&q=` 返回 `{items: [...], total, page, page_size, pages}`（分页包裹）。
   - 保持 `GET /api/tickets/all` 行为不变（供 operator/admin 无分页视图，若需要亦可加参数，默认继续全量以兼容现有调用）。
4. 参数解析、边界校验（page≥1、page_size 1–100）、非法值回退默认。

**前端（`web/lib/api.ts` + `web/app/tickets/page.tsxx`）—— 责任人：前端**
1. `api.ts`：新增 `listTicketsPaginated({page, page_size, status, q})`，返回分页对象。
2. 页内新增分页状态：
   - `const [page, setPage] = useState(1)`
   - `const [pageSize] = useState(20)`
   - `const [total, setTotal] = useState(0)`
   - `const [listLoading, setListLoading] = useState(false)`
3. 列表加载改为 `useEffect` 依赖 `[filter, q, page]`：触发时请求后端分页接口，写 `items`。
4. 移除前端本地 `filtered` 的过滤逻辑（改为由后端过滤），保留搜索输入 `q` 作为请求参数。
5. 分页 UI 组件：底部 `上一页 / 页码(s) / 下一页` + `共 N 条 · 第 x / y 页`；页码可点击，支持省略号（`1 … 4 5 6 … 20`）。
6. **联动规则**：
   - 切换筛选 Tab 或输入搜索（防抖 300ms）→ 重置 `page=1` 并重新请求。
   - 删除某条后若当前页被删空则自动回退 `page=page-1`（至少 1）。
   - 新建工单后回到第 1 页并刷新，保证新单可见。
   - 选中工单的实时轮询（`active` 工单对话）**不受列表分页影响**，仅刷新单卡数据而非整表。

**验收标准（本模块）**
- 100 条数据下，首屏仅请求 20 条；切换页/筛选/搜索均正确返回对应子集，`total/pages` 元数据准确。
- 搜索与筛选：搜索命中数与后端 `count` 一致；切换筛选后仍能搜索、翻页正确。
- 分页 UI 无闪烁抖动、加载中有占位/骨架态；快速连点翻页无竞态（以最新请求覆盖旧请求，`AbortController` 或请求序号校验）。
- 页数超过 7 页时省略号正确。

## 3. 需求③：新建工单交互体验优化

### 3.1 设计目标
- 用户点击**「创建并运行」后立即关弹窗进入聊天页**，不再被同步校验阻塞。
- 在聊天框内**按阶段实时（流式）展示**：`相关性校验 → 内容重写 → 意图/风险分类 → 开始执行 → 逐步输出（知识检索/工具/结论）→ 待确认完成`。
- LLM 后台推理时，聊天框渲染**带跳动动效的「🔄 大模型思考中…」**提示条。
- 相关性不通过时，在聊天框内以红色系统消息提示拒绝原因，工单不落地（或落地为失败态并在聊天中说明，采用**前者：不落地**，保持一致）。

### 3.2 技术方案

**核心：将建单链路由"同步阻塞"改为"快速落单 + 后台异步执行 + 事件流推送"。**

现链路 `POST /api/tickets` 同步做 3 次 LLM。改造后：

**后端（`app/api/tickets.py` + `app/orchestrator.py` + `app/classifier.py`）—— 责任人：后端**
1. **快速落单接口**：`POST /api/tickets` 改为**只做最小校验（长度/权限）立即建单**（status=`created`，risk/intent 暂默认），返回 `ticket_id`；不再同步做相关性/重写/分类。
2. **异步执行脚本化**：把 `relevance_check → rewrite_content → classify` 移入可后台执行流程，将**每个阶段的进行/结果/失败**写成 `ticket_events` 新事件类型（建议复用现有机制，新增/启用事件类型如 `stage`，payload `{stage:"relevance"|"rewrite"|"classify"|"exec", state:"running"|"ok"|"fail", summary}`）。
   - `stage running/summary` 供前端流式展示各阶段标题与结果摘要。
   - 相关性不通过：写 `system_message`（拒绝原因）+ 置状态 `cancelled`，结束，不触发 Agent。
3. **触发执行**：前端调 `POST /api/tickets/{id}/run`（现成接口）触发异步编排；编排内部按阶段发事件。
4. 保持既有 `ticket_events` 审计与 `state_transition` 不变。

**前端（`web/app/tickets/page.tsxx` + `web/lib/api.ts`）—— 责任人：前端**
1. `submit()` 改为：`await createTicket(form)`（快速，秒级返回）→ 立即 `setModalOpen(false)`、`setActive(t.id)` 进入聊天页 → 订阅该工单 WS（现有 `subscribeTicketWS`）→ `runTicket(t.id)`。
2. **聊天流式展示**：状态机扩展 `eventToMsg`，将新 `stage` 事件渲染为居中系统工具条（例："① 相关性校验… ✅ 通过 → ② 内容重写… ✅ → ③ 意图/风险分类… ✅ → ④ 开始执行"）。
3. **思考动效**：新增 state `thinking`（由 stage=exec 触发或由 WS/轮询判断 `pending` 进行中状态驱动）；渲染 `div.thinking` 内含三个跳动圆点 + "大模型思考中…"；对应加到 `MsgView` / 对话尾部。
4. 建单失败（HTTP 4xx：含长度/权限/相关性拒绝）分支：若已快速建单则聊天内显示拒绝原因；弹窗内仅显示表单校验错误。

**验收标准（本模块）**
- 点击「创建并运行」→ 弹窗关闭、进入聊天页 **<500ms**（快速落单），全程无"校验中…"空白等待。
- 聊天页依次出现 相关性→重写→分类→执行 的阶段进行/完成提示，**顺序正确**。
- LLM 推理期间出现跳动「大模型思考中…」；完成后消失并进入"待确认完成"确认条。
- 相关性拒绝场景：聊天框内出现红色拒绝原因提示，工单状态为「已取消」，不触发 Agent 执行。
- 阶段进度经 WS 实时推送，断开 WS 时可由轮询兜底（活跃工单轮询已存在）。

## 4. 开发优先级

| 优先级 | 需求 | 理由 |
|---|---|---|
| **P0** | ③新建工单交互优化 | 用户痛点最直接（无反馈等待），改动集中在建单链路，收益最高 | 
| **P1** | ②分页功能 | 影响加载性能与可扩展性，涉及前后端全链路，需尽早打通接口契约 |
| **P1** | ①页面布局调整 | 纯前端、低风险、见效快，可与②的前端工作合并推进 |

> 组合推进策略：**①②** 都落在 `tickets` 页面与 CSS，可合并为一个前端迭代包并行开发；**③** 独立走建单链路。因此排期为两线并行，见 §6。

## 7. 联调安排

- **联调入口**：http://127.0.0.1（nginx:80 → web:3000 / app:8000）

  1. 建单（相关）→ 聊天页流式 4 阶段 → 思考动效出现→消失 → 待确认完成。

## 10. 风险与回退

| 风险 | 应对 |
|---|---|
| ③ 快速落单后相关性拒绝需回滚已建工单 | 采用"不落地"策略：后台校验不通过时写 system_message 并置 cancelled，前端提示；上线前在 mock/真 LLM 双重验证 |
| ③ 改造触碰验收不通过时的既有"弹窗内显示拒绝原因" | 保留弹窗表单校验路径（长度/必填），仅把 LLM 类校验移到聊天流式 |
| ② 后端分页接口变更破坏 `all`/其它调用方 | `all` 接口保持兼容；分页返回包裹新结构，前端同步升级，单次发布 |
| ① 响应式改动影响既有审批页观感 | 只改 `.ticket-layout` 域内样式，隔离作用范围 |
| WS 断开导致阶段进度丢失 | 活跃工单轮询兜底重建 `msgs`；思考态由轮询状态判定补齐 |
