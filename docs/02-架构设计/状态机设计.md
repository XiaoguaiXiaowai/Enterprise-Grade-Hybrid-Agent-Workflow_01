# 状态机设计

> 状态：现行 · 最后校验：2026-08-18 · 校验方式：符号级 + 行为实测（`scripts/run_all_tests.py`）
> 一句话：**用确定性状态机约束工单流转，禁止跳步/非法转移，每一步落审计事件**——这是「可靠」的根基。
> 实现：`app/state_machine.py`（定义与校验）+ `app/daos/tickets.py:transition`（持久化与乐观锁）；功能面见 [01-企业级Agent-Harness.md](../01-核心功能/01-企业级Agent-Harness.md)。

---

## 1. 状态全集

`app/state_machine.py` 的 `VALID_STATUSES`：

```
created  triaged  gathering  agent_running  awaiting_approval  running
pending_confirm  done  failed  cancelled  archived
```

> ⚠️ `running` 为**历史遗留状态**（M2 早期命名）：仅保留在状态机定义中防止历史数据校验失败，**无代码路径转入**。当前编排统一使用 `agent_running`。

## 2. 转移表（`TRANSITIONS`，当前实现）

| from | to |
|---|---|
| `created` | `triaged`, `cancelled` |
| `triaged` | `gathering`, `failed`, `cancelled` |
| `gathering` | `agent_running`, `awaiting_approval`, `failed`, `cancelled` |
| `agent_running` | `gathering`, `awaiting_approval`, `pending_confirm`, `failed`, `cancelled` |
| `awaiting_approval` | `running`*, `gathering`, `cancelled`, `failed` |
| `running`* | `done`, `failed`, `cancelled`（历史遗留，无代码路径） |
| `pending_confirm` | `done`, `gathering`, `cancelled` |
| `done` | `archived` |
| `failed` | `archived`, `gathering`, `cancelled` |
| `cancelled` | `archived` |
| `archived` | — |

## 3. 关键语义（与直觉不同的地方，面试重点）

1. **`agent_running` 不能直接 → `done`**：回合收敛先到 `pending_confirm`（待客户确认完成），客户 `POST /api/tickets/{id}/confirm` 确认后才 `done`——**终态由人确认，不由模型自封**。
2. **收敛语义**：模型回合给出 `done` 判定后，orchestrator 置 `pending_confirm`（`orchestrator.py:404`）；确认 → `done`；追问 → 回 `gathering` 开新一轮；放弃 → `cancelled`。
3. **审批恢复路径**：`awaiting_approval` 审批通过后不直接回 `agent_running`，而是经 `gathering → agent_running → pending_confirm` 完整走一遍（`orchestrator._finalize_after_sdk_resume`：状态机不允许 `awaiting_approval → pending_confirm` 直跳）。
4. **预算/超时/停止条件触顶 → `failed`**（不是 cancelled）；`failed` 允许补充信息后重试（→ `gathering`）或放弃（→ `cancelled`）。
5. **`cancelled` 只能由人触发**（`POST /api/tickets/{id}/cancel`）；`agent_running` 执行中不可取消（409），需等本回合结束进入 `pending_confirm`/`awaiting_approval` 后取消。
6. **建单即入状态机**：快速落单后分类流水线移到 run 阶段（`_entry_stages`）；相关性不通过 → `cancelled` + 拒绝文案（不是 422 拒绝）。

## 4. 持久化与并发安全（`app/daos/tickets.py:transition`）

- 单一写入口：`UPDATE tickets SET status=? WHERE id=? AND status=?` **条件更新（乐观锁）**，rowcount≠1 抛 `InvalidTransition`——多副本部署下防竞态；
- 每次转移写 `ticket_events`（`add_event`，类型 `state_transition`），形成完整审计链；
- 进程内另有 `app/taskqueue.py:try_acquire` 每工单互斥锁，双保险防并发双跑。

## 5. 设计取舍

- **不用 LangGraph**：状态转移表 + 乐观锁实现简单、可逐行讲解，快照/HITL 原理完全可控；
- **状态外部化（DB）而非内存**：进程重启/多副本不丢状态，恢复链路（`resume_ticket`/`resume_run`）都依赖 DB 状态；
- **校验与执行分离**：`can_transition` 纯函数（可单测），`transition` 负责持久化，非法转移在边界层即被拦截。
