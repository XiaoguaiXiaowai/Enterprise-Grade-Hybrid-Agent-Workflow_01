# 面试文档 —— 企业级混合 Agent 工作流 Demo

> 用途：自我介绍、Demo 现场演示讲稿、8 大能力讲法、追问与深度预案。
> 配套：`README.md`（一张图开场）、`doc/开发文档.md`（技术全貌）、M1/M2/M3/M4 README（阶段说明）。

---

## 1. 一句话定位（开场必背）

> "我搭的是一个**企业级 Agent 收拢件（Harness）**：它不是一个'让 AI 更聪明的 Demo'，而是展示 **AI 如何被可靠、可控、可审计地接进企业业务**。我以 IT 工单为载体，把大模型当作'判断层'，把执行权交给确定性的流程、权限与审批。"

**三个关键词**（贯穿全场，反复用）：
- **可靠**（Reliable）：状态机、幂等、预算、停止条件 —— 不跑飞
- **可控**（Controlled）：IAM 最小权限、工具白名单、HITL 审批 —— 不越权
- **可审计**（Auditable）：Trace 全链路、监控指标 —— 出错能查

## 2. 30 秒电梯介绍（自我介绍用）

"我实现了一个企业 IT 工单处理系统，覆盖从**身份校验 → 风险分级 → Agent 循环 → 人工审批 → 审计交付**的完整闭环。技术栈是 Python + FastAPI 做后端 Harness，自研状态机而非套 LangGraph，LLM 支持 OpenAI 和 Ollama 双切换，前端 Next.js，单机 Docker 部署。它把大模型的 8 类工程问题——上下文管理、模型路由、权限隔离、工具安全、HITL、预算、Trace、监控——全部落地成了可运行的代码。"

## 3. Demo 演示脚本（10-12 分钟版）

> 准备：`docker compose up -d --build` 后访问 `http://<IP>/`，登录页。

### 3.1 开场 · 首页/流程图（1 分钟）
- 打开 README 的架构图（或 `doc/开发文档.md` 架构图），强调"这是 harness 而非单模型应用"
- **话术**："看右下角这 8 大模块，今天我会带你把它们挨个在真实工单里走一遍。"

### 3.2 登录 · 身份与租户（40 秒）
- 用 `admin` 登录，再快速展示角色概念（employee/operator/admin）
- **讲点**：不同角色装配到 Agent 的工具集不同（RBAC 层面收到的工具是过滤过的）

### 3.3 建工单 · 风险分级（1 分钟）
- 建一张**高风险**："给 u-1024 开通数据库只读账号"
- 讲点：
  - 入口做了**风险分级**（low/medium/high），高风险不等于拒绝，而是进入**审批**
  - 输入即结构化（标题/描述/风险/意图），避免"模糊目标"导致 Agent 跑偏

### 3.4 运行 · LOOP 与上下文装配（2 分钟）
- 点"运行"，看实时 SSE 事件流刷出：`created → triaged → gathering → agent_running`
- 讲点：
  - **上下文装配**：系统不是把所有历史全塞给模型，而是"选/压/截"——只带这一圈真正需要的（目标/状态/近 N 条历史/工具清单/约束/剩余预算）
  - **模型路由**：意图=变更 → 路由到更强的模型（默认配置里高风险升格）
  - **工具白名单**：模型只能在注册表里选工具，防幻觉调用（不存在的工具直接拒绝）

### 3.5 触发 HITL · 人工审批（2 分钟）
- Agent 规划要调用 `grant_db_readonly`（高危工具）→ 工单进入 `awaiting_approval`
- 切到审批台，`operator` 看到待审单 → 点"通过"
- 讲点（核心，面试官最感兴趣）：
  - **三层安全约束**：最小权限凭证 → 参数强校验 → 幂等状态机；HITL 是第四层"人接管权"
  - 高危动作的执行权**从 Agent 手里收回**，改成"申请-审批"模式
  - **M4 演进**：高风险工具用 SDK 的 `function_tool(needs_approval=True)` → 原生 **interruptions**，
    审批通过后用 `Runner.run_sync(agent, state)` 从同一 RunState 恢复（多 Agent 下也成立）；
    `_PENDING` 内存注册表持久化审批待恢复信息

### 3.6 Trace · 审计回放（1 分钟）
- 打开该工单的 Trace 页，展示时间线：模型/Provider、工具、状态变化、延迟
- 讲点：每次模型调用和工具调用都落库，含**模型版本、提示词版本、上下文来源、参数、结果、状态前后、耗时** —— 出问题能精确回放是哪一步

### 3.7 指标 · 监控评估（40 秒）
- 打开 `/metrics`，展示成功率/正确失败率/延迟/成本/人工接管率
- 讲点："人工接管率"是 harness 特有的指标：它反映系统把多少决策正确地还给了人

### 3.8 收尾 · 可演进性（1 分钟）
"这套现在单机跑，但架构是可演进的：切 Ollama 只改配置、走 SSO 有迁移点、上 K8s 把状态外置即可。**今天演示的是最小闭环，但它每一层都能在生产里找到对应物。**"

**演示冷启动兜底**：若模型未配置，默认 `reader` 后端仍能完整走通 HITL/Trace/指标（不需要真模型），保证面试现场不翻车。

## 4. 项目架构自述（技术面试通用）

### 4.1 技术栈一句话
- 后端：Python + FastAPI + SQLite（WAL，单机零成本）
- 编排：**自研状态机**（显式 `TRANSITIONS` 表，禁止跳步）管治理；**OpenAI Agents SDK**（`Agent+Runner`）管 LLM 循环与多 Agent handoff
- LLM：SDK `RouterProvider` 路由 **OpenRouter（主）⇄ Ollama（兜底）**；`llm_gateway.py` 作离线 `reader` 兜底
- 前端：Next.js 14（App Router，纯客户端 SPA）
- 部署：Docker Compose + Nginx 反代，单台 Ubuntu

### 4.2 为什么自研状态机，不用 LangGraph/框架
- **讲法**："我用官方 **OpenAI Agents SDK** 接管'LLM 计划-工具循环'与多 Agent handoff（这是它擅长、且我不想重复造轮子的部分），但企业治理层仍然**自研**：状态机（显式 `TRANSITIONS` 表）、预算、守卫、审批持久化、Trace 全部在 SDK 之外由 Harness 掌控。为什么不全用 LangGraph 这类通用编排框架？因为它把 checkpoint/interrupt/HITL 做成黑盒，我自研的状态机 + SDK 原生 interruptions，每一行都能讲清'HITL 怎么中断、又怎么恢复'。"
- 加分点：这正好呼应笔记里的"约束 3：确定性流程引擎"—— **Agent 的动作序列必须由确定性 Workflow 管理，防止跳步/重复**；LLM 只负责判断，执行权在 Harness。

### 4.3 请求全链路（一句背下来）
"登录拿 token → 鉴权 → 建单做风险分级 → `run_ticket` 推进状态机 → SDK 拉起 TriageAgent → handoff 到对应子 Agent（知识/身份/变更）→ Agent 调用工具（白名单/幂等，高风险触发 SDK 原生审批中断）→ 审批通过用 RunState 恢复 → 收敛校验 → 写 Trace 与指标 → 交付。"

## 5. 8 大能力 · 面试讲法（每条 20-30 秒）

| # | 能力 | 一句话讲法 | 证据点（代码） |
|---|---|---|---|
| 1 | 流程定义 | 把模糊需求结构化，明确"哪些交给 Agent、哪些交给 Workflow"，划风险边界 | `ticket` 结构化字段 + 状态机唯一编排 |

## 6. 高频问题与回答（QA 预案）

### Q1：为什么不用 LangGraph / AutoGen 这些 Agent 框架？
答：见 4.2。再加一句——"LLM 循环我直接用官方 **OpenAI Agents SDK**（工具循环/多 Agent handoff 是它擅长且成熟的部分），但**企业治理层**（状态机/审批/预算/审计）我保留自研，不交给通用编排框架的黑盒。这样既有 SDK 的多 Agent 编排能力，又守住'可靠、可控、可审计'。"

### Q2：如何防止提示注入 / Agent 越权？
答：三层防护——
1. 工具结果按 content 类型处理，不把工具输出里的指令当系统指令
2. 工具参数进强类型校验，非法直接拒
3. 工具**白名单**注册表，模型只能调用已登记工具
（落点：`skills/registry.py` 里 `invoke` 未知工具即拒绝）

### Q3：上下文越来越大怎么办？（Auto-Compact）
答："我实现了三件事：选（只带这一圈需要的）、压（长 observation 先压缩）、截（超阈值把早期历史压成一段摘要，给关键状态留空间）。这正是笔记里的 Auto-Compact，避免模型被无关历史'自我污染'。" 代码：`context_assembler.py`

### Q4：HITL 中断/恢复不是会丢上下文吗？
答："不会。M4 起用 SDK 原生 interrupts：模型调用高危工具 → `RunResult.interruptions` 得到 `ToolApprovalItem`，我把参数写进 `approvals` 表并把整个 `RunState` 存进内存注册表，工单转 `awaiting_approval`。审批通过后 `state.approve(item)` 再 `Runner.run_sync(agent, state)` **从同一 run 继续**（含已发生的多 Agent handoff），不重跑整轮。"

### Q5：模型想调用一个不存在的工具怎么办？
答："`registry.invoke` 第一个判断就是工具是否登记，未登记直接返回**失败**并拒绝执行。这就是笔记里的'工具发现与版本管理：硬编码确认为主，防幻觉调用'。"

### Q6：如何验证 Agent 没跑偏 / 预算失控？
答："双重保险：状态机约束动作序列不能跳步；三重预算（步数/Token/时间）每步 `consume_step` 触顶即 `failed` 终止。收敛时还要模型输出 `done:true` + 规则校验器确认产物完整性。"

### Q7：多租户怎么做隔离？
答："所有数据表带 `tenant_id`，查询强制加租户条件（代码里 `row["tenant_id"] != ctx["tenant_id"]` 直接 403）；工具装配按角色过滤。这是物理隔离，不依赖模型自觉。"

### Q8：OpenAI 和 Ollama 怎么切换？
答："M4 起，OpenRouter（主）与 Ollama（兜底）都走 `/v1/chat/completions` 协议，由 SDK 的 `RouterProvider` 按模型名前缀（`openrouter:`/`ollama:`）路由，`.env` 里按场景设主/兜底键（`AGENT_MODEL`/`AGENT_FALLBACK_MODEL`、`CLASSIFIER_*` 等，完整清单见 `doc/模型配置清单.md`）即可切换模型，所有模型参数与 Ollama 服务器地址均可配置。OpenRouter 失败自动切 Ollama，均不可用回退离线 `reader` 保证演示不翻车。"

### Q9：数据敏感信息怎么办？
答："`masker.py`：姓名→`张*`、邮箱→`z****@corp.com`、密码/令牌→`***`。工具返回值先脱敏再喂回模型，模型不会拿到明文凭证。"

### Q10：为什么是这种 Demo 而非通用聊天 Agent？
答："因为我要展示的不是'模型能力'，而是**工程能力**——**把大模型安全接进企业业务的能力**，这才是 AI 开发工程师的核心竞争力。"

## 7. 深挖层（面试官可能追问到代码）

### 7.1 幂等
- 每个高危工具生成 `idempotency_key = fingerprint(ticket, tool, params)`
- `guards.is_duplicate` 查 `tool_calls`：同参数时间窗内已成功 → 拦截
- 恢复执行不会重复下发权限；失败有补偿工具 `revoke_db_readonly`

### 7.2 状态机为什么这么设计
- `state_machine.py` 的 `TRANSITIONS` 是显式映射，"禁止跳步"在 `transition()` 里硬校验
- 每次转移写 `ticket_events` 审计（from/to/actor/reason）→ 状态可追溯

### 7.3 模型路由策略
- `model_router.route(intent, risk)`：知识→轻量，变更/故障→强模型，高风险升格
- 成本与质量平衡（呼应"模型路由：根据条件自动调用对应模型"）

### 7.4 预算的实现细节
- `budget.consume_step(tokens)` 每步自增并 `check()`，超 `max_steps/max_tokens/max_seconds` 抛 `BudgetExceeded`
- orchestrator catch 后工单转 `failed`，不会无限循环

## 8. 如果被问到"项目中最大的难点/收获"

> "最大的难点不是让模型回答问题，而是**把'不可控'的 Agent 变成'可控'的流程**。我最大的收获是理解到：企业级 Agent 的工程重心在 harness——权限、审批、预算、审计——而不是模型本身。这也是我为什么自研状态机而不是套框架：因为只有自己写的，才敢在面试里逐行讲清楚它是怎么保证可靠、可控、可审计的。"
