## 一、状态机与收敛约定（先读）

### 1.1 完整转移表

来源：`app/state_machine.py`（`TRANSITIONS`）。注意 `running` 为历史遗留状态（M2 早期命名），当前编排统一使用 `agent_running`，无任何代码路径转入 `running`。

| 当前状态 | 允许转移 | 说明 |
|---|---|---|
| `created` | `triaged`、`cancelled` | 建单即 created；相关性不通过直接 cancelled |
| `triaged` | `gathering`、`failed`、`cancelled` | 分类后进入 LOOP |
| `gathering` | `agent_running`、`awaiting_approval`、`failed`、`cancelled` | 装配上下文 |
| `agent_running` | `gathering`、`awaiting_approval`、`pending_confirm`、`failed`、`cancelled` | 执行中；HITL 中断 → awaiting_approval |
| `awaiting_approval` | `running`、`gathering`、`cancelled`、`failed` | 审批恢复 → gathering；取消 → cancelled |
| `running` | `done`、`failed`、`cancelled` | 历史遗留，无转入路径 |
| `pending_confirm` | `done`、`gathering`、`cancelled` | 确认完成 → done；追加追问 → gathering；取消 → cancelled |
| `done` | `archived` | 终态（不再允许追问） |
| `failed` | `archived`、`gathering`、`cancelled` | 补充信息后重试 → gathering；放弃 → cancelled |
| `cancelled` | `archived` | 终态 |
| `archived` | （无） | 终态 |

### 1.2 收敛流程与 pending_confirm 语义

- 当前收敛流程：`agent_running → pending_confirm`（回合完成，待客户确认）→ `POST /api/tickets/{id}/confirm` → `done`。
- `_run_loop`（`app/orchestrator.py`）在回合结束时把工单状态置为 `pending_confirm`，返回的 run 结果 status 为 `done`——**脚本断言时区分「run 返回 status」与「工单表 status」**：run 返回 `done` ≠ 工单状态 `done`（工单此时是 `pending_confirm`）。
- `POST /api/tickets/{id}/messages`（追问）：仅 `pending_confirm` / `failed` 放行开新一轮（`_run_loop` 经 `gathering → agent_running → …` 重新收敛）；`created/triaged/gathering/agent_running/running/awaiting_approval/done/archived` 一律 409 拒绝（`app/api/tickets.py:followup`）。
- `POST /api/tickets/{id}/confirm`：仅 `pending_confirm` 可确认 → `done`（终态），其余状态 409（`app/api/tickets.py:confirm`）。
- `POST /api/tickets/{id}/cancel`：`agent_running/running/done/archived/cancelled` 不可取消（409），其余状态取消 → `cancelled`，未决审批一并置 `rejected`（`app/api/tickets.py:cancel`）。
- **审批驳回不直接 cancelled**：`POST /api/tickets/{id}/approve` 的 reject 分支经后台任务调 `resume_ticket(..., decision="reject")`，SDK 路径由 `app/agents_runner.py:resume_run` 让模型得知驳回并调整策略，随后收敛到 `pending_confirm` 或再次 `awaiting_approval`；`cancelled` 只由 cancel 端点或相关性校验未通过产生。
- **分类永不 failed**：`classify`（`app/classifier.py`）LLM 失败 → 关键词规则兜底（`source="rule"`，classifier.py:123-126）；相关性校验不通过 → 写拒绝文案并 `cancelled`（`app/orchestrator.py:_entry_stages`，orchestrator.py:205）。
- run / 追问 / 审批端点均已后台任务化：返回 `{"status":"queued"}`（`app/taskqueue.py` + `app/api/tickets.py:run`），断言终态需轮询工单状态或经 WS/事件流。

## 四、单测现状与建议新增

`tests/` 目前只有 `tests/test_model_config.py`（16 用例，14 过，见 §7.2）。以下五类单测尚无独立文件，建议按模板新增（全部 🔌 离线可测，断言均指向已核实的真实符号）：

1. **状态机跳步**（`app/state_machine.py:can_transition` / `InvalidTransition`）
   - 断言 `can_transition("created","done") is False`；`can_transition("pending_confirm","done") is True`；`can_transition("done","gathering") is False`（done 为终态）；`daos.transition` 对非法跳步抛异常且工单状态不变。
2. **守卫幂等**（`app/guards.py:is_duplicate` / `fingerprint`）
   - 同工单同参两次调用，窗口内第二次 `is_duplicate` 返回 True；`fingerprint` 对相同 (scope, tool, params) 稳定、对参数顺序不敏感。
3. **预算触顶**（`app/budget.py:Budget` / `BudgetExceeded`）
   - `Budget(max_steps=1, ...)` 构造后 `consume_step()` 抛 `BudgetExceeded("steps", ...)`；`left` 属性不为负。
4. **模型路由升格**（`app/model_router.py:route`）
   - 未显式设 `AGENT_MODEL` 时 `route("change","high")["model"] == settings.router_model_high_risk`；`route("knowledge","low")` 用 `router_model_default`；无 `OPENROUTER_API_KEY` 时 `provider == "ollama"`。
5. **分类永不 failed / 模型熔断**（`app/classifier.py:classify`、`app/llm_gateway.py:chat_with_fallback`）
   - LLM 不可达时 `classify()` 返回 `source="rule"` 且不抛异常（classifier.py:123-126）；`chat_with_fallback` 主用 → Ollama → reader 三级熔断——`tests/test_model_config.py` 已覆盖这两项（`test_classifier_fallback_to_rules`、`test_chat_fallback_*`），可直接作为参照。

## 六、审计断言要点

- **metrics 字段**（`app/metrics.py:aggregate` / `aggregate_range`）：`tickets`、`success_rate`、`correct_failure_rate`、`avg_latency_ms`、`total_cost`、`human_takeover_rate`；写入入口 `app/metrics.py:record`（success / correct_failure / latency_ms / cost / human_takeover）。
- **trace 字段**（`app/trace.py:write` / `list_for_ticket`）：`req_id`、`ticket_id`、`model`、`provider`、`prompt_version`、`context_source`、`tool_name`、`io_json`、`state_before`、`state_after`、`latency_ms`、`token_usage_json`、`retry_count`。
- **prompt_version 单一来源**：`app/agents_runner.py` 的 `PROMPT_VERSION = "M4-agents"`；传统链路 `_plan_and_execute`（orchestrator.py:538）与 SDK 链路写同一常量——**不能用 prompt_version 区分 SDK/传统链路**，应看 trace `provider`（`reader` 即降级链路）或事件类型。

## 七、已知红项与注意事项

### 7.1 `scripts/smoke.py` 断言过时（勿推荐为主）

`scripts/smoke.py` 为 M1 期脚本，`assert ticket["status"] == "done"` 仍按"回合直接 done"断言，与现行 `pending_confirm` 收敛语义冲突，**当前运行会 FAIL**。主冒烟请用 `scripts/smoke_m2.py` / `scripts/run_all_tests.py`。

### 7.2 空值覆盖默认：verify_model_config / test_model_config 当前红

`.env` 中 `EMBEDDING_MODEL=`（空串）经 `load_dotenv` 进入环境后，`os.getenv("EMBEDDING_MODEL", 默认)` 返回空串而非代码默认 → 依赖"默认 nemotron embedding"的断言失败。实测：

- `tests/test_model_config.py`：14/16，红项 `test_settings_env_priority`、`test_newfeature_model_override_and_fallback`；
- `scripts/verify_model_config.py`：FAIL。

行为归属与说明见 [配置清单.md](../03-部署运维/配置清单.md) §13「已知陷阱」第 1 条。文档/脚本断言"默认值"时必须先清除该键。

### 7.3 `run_all_tests.py` 的 env 覆盖机制（实测）

- `settings` 在 `import app.config` 时实例化并冻结，之后改 `os.environ` **不生效**。
- 脚本内 `_new_db` 对 `APP_DB_PATH` 的改写发生在 app 导入之后 → **无效**：实测 `/tmp/wf_offline.db`、`/tmp/wf_sdk.db` 从未被创建。
- **不加前缀直接跑会落在 `.env` 的 `APP_DB_PATH=./data/app.db` 上并写入测试工单**（实测一次 offline 组新增 3 张测试工单，会污染演示数据）。
- 命令行前缀 `APP_DB_PATH=/tmp/wf_test.db .venv/bin/python scripts/run_all_tests.py offline` **有效**（import 前已设置，实测按前缀建库）——这是推荐的隔离方式。
- offline 组的 `OPENROUTER_API_KEY=""` / `OLLAMA_BASE_URL` 指向不可达地址 / `at._SDK_OK=False` 均设置在 import 之前 → 有效，保证确定性 reader 链路。

### 7.4 脚本内编号冲突

`scripts/run_all_tests.py` 注释中的「T15」实为**取消流程**用例（awaiting_approval → cancelled、未决审批作废），与本文 T15「状态机非法跳步」不是一回事，引用时注意。

### 7.5 `smoke_m2.py` 需真实可达模型后端

`smoke_m2.py` 不强制关闭 SDK：SDK 已安装（`agents` 包可导入）且模型后端不可达时，`run_sdk` 抛 `RuntimeError("Agent 执行失败: ...")` → 工单 `failed`（实测：强制离线跑 smoke_m2，reason=`Agent 执行失败: Connection error.`）。它使用 `setdefault APP_DB_PATH=/tmp/m2_smoke.db` 隔离库。要与 `run_all_tests.py offline` 的确定性 reader 行为区分——后者显式 `at._SDK_OK=False`。
