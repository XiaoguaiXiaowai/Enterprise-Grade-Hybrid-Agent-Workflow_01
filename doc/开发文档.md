# 企业级混合 Agent 工作流 Demo —— 开发文档

## 1. 项目总览

### 1.1 一句话定位

一个跑在单台 Ubuntu 服务器上的**企业 IT 工单智能处理系统**，用于完整展示"企业级 Agent Harness"的 8 大工程能力：它不是演示"AI 多聪明"，而是演示"AI 如何被可靠、可控、可审计地接进企业业务"。

### 1.2 IT 工单特点

- 天然存在**风险分级**：查知识库 / 查 CMDB 是低风险只读操作，可直接执行；改权限 / 重启生产服务 / 发通知是高危操作，必须 HITL 审批
- 天然长得出**工具面**：只读查询 vs 变更执行，正好演示"最小权限 + 硬编码白名单 + 参数强校验 + 审计"
- 与"AI 开发工程师"岗位叙事契合：研发团队自己就能理解、能代入

## 2. 业务设计

### 2.1 四类可演示工单

| 类型   | 例子                    | 风险级别 | 处理方式                      |
| ---- | --------------------- | ---- | ------------------------- |
| 知识查询 | "VPN 连不上怎么办？"         | 低    | 单 Agent 走 RAG 直接回答        |
| 数据查询 | "查用户 u-1024 的权限"      | 中    | 只读工具 + 脱敏 + 结果确认（可选 HITL） |
| 变更操作 | "给 u-1024 开通 DB 只读账号" | 高    | 多 Agent + HITL 审批 + 幂等执行  |
| 故障排查 | "生产服务 A 最近 5 分钟 502"  | 中/高  | 诊断链 + 修复计划 + 审批后才能执行变更    |

### 2.2 工单状态机

```text
created → triaged（意图分类+风险分级）
       → gathering（上下文装配/RAG）
       → agent_running（LOOP 执行）
       → awaiting_approval（HITL 中断）
       → running（审批通过后执行）
       → done / failed / cancelled
       → archived（任务状态归档，事件只读）
```

每个转移都记录 actor、reason、timestamp，形成状态审计链。

### 2.3 角色与权限矩阵（RBAC 落地）

| 角色       | 建单    | 读工单       | 审批     | 管理工具 | 审计/指标 |
| -------- | ----- | --------- | ------ | ---- | ----- |
| employee | ✅（本人） | ✅（本人/租户内） | ❌      | ❌    | ❌     |
| operator | ✅     | ✅         | ✅（高/中） | ❌    | ❄     |
| admin    | ✅     | ✅ 全部      | ✅      | ✅    | ✅     |

工具级权限：每个工具声明 `allowed_roles`，`tool_registry` 在装配时按当前身份过滤 → 实现"只给真正需要的工具"。

### 2.4 风险分级输入（入口层演示点）

```python
RISK_RULES = [
    Rule(pattern="开通|授权|删除|重启|重置", risk="high"),
    Rule(pattern="查询|查看|如何|为什么", risk="low"),
    ...
]
```

由规则引擎**分级**；再由模型**复评**，若模型上调风险级别则覆盖（模型仅在"更严格"方向覆盖）。

## 3. 系统架构（Harness 核心）

### 3.1 Workflow 编排（自研状态机，不用 LangGraph）

```python
# orchestrator.py —— 与笔记"约束3：确定性流程引擎"对应
STATE_TRANSITIONS = {
    "created":        {"triaged"},
    "triaged":        {"gathering", "failed"},
    "gathering":      {"agent_running", "awaiting_approval", "failed"},
    "agent_running":  {"gathering", "awaiting_approval", "done", "failed", "cancelled"},
    "awaiting_approval": {"running", "cancelled", "gathering"},
    "running":        {"done", "failed", "cancelled"},
    "done":           {"archived"},
}
def transition(ticket_id, to, actor, reason):
    state = store.get_state(ticket_id)
    if to not in STATE_TRANSITIONS[state]: raise InvalidTransition(...)
    state = store.set_state(ticket_id, to, actor, reason)  # 单事务 + 审计
```

### 3.2 核心 LOOP 装配上下文（笔记"选/压/截 + 结构化"）

```python
def assemble_context(ticket, history, memo, artifacts, tools, budget, risk):
    ctx = Context()  # 有序 + 齐全，避免"自我污染"
    ctx.goal   = ticket.goal            # 原始目标（From 状态）
    ctx.state  = ticket.current         # 当前状态
    ctx.history = compress(history, budget)   # 选/压/截：>N 条先摘要
    ctx.memo   = memo.relevant(ticket)  # 长期记忆（按需注入）
    ctx.artifacts = artifacts.recent(3) # 关键产物，不全带
    ctx.tools  = tools.allowed_for(actor, ticket.risk)  # 动态分配
    ctx.constraints = ["仅执行低/中风险操作", f"权限:{actor.role}", ...]
    ctx.budget_left = budget.left()
    return ctx
```

### 3.3 四层安全约束落实

| 备注层           | 实现                                                                                  | 关键文件                                  |
| ------------- | ----------------------------------------------------------------------------------- | ------------------------------------- |
| 1 权限与身份层      | 工具不持全权凭证；执行前按 actor 身份换取**最小权限临时凭证**（本地实现：operator/admin 才可见写权限工具）                  | `auth.py` `skills/`                   |
| 2 工具调用层       | 每个工具声明 JSON Schema；execute 前置强校验 + 非法参数拦截；防 prompt injection（工具结果中剥离指令性文本进 content） | `skills/schemas.py`                   |
| 3 执行流程层       | 状态机约束 + `idempotency_key`（防重复执行） + 补偿（失败事务回滚式日志）                                    | `orchestrator.py` `skills/storage.py` |
| 4 安全合规层(HITL) | 高风险工具进入 `awaiting_approval`，仅返回"申请单"；审批人通过管理员 API 批准                                | `approval.py`                         |

### 3.4 工具层 MPC Skill 化

每个工具一个文件，统一接口：

```python
@register_tool
def grant_db_readonly(params, ctx):
    # 1 IAM：ctx 已验证角色；2 白名单：仅白名单操作
    # 3 参数校验：schema 强校验；4 脱敏：返回值先过 masker
    # 5 HITL：高风险动作转审批；6 幂等/重试/补偿
    # 7 审计：trace 记录 名/参/返回/耗时/状态
```

内置工具清单（演示用，全部可逆、不碰真实生产）：

- `search_kb`（低）：RAG 查企业知识库
- `query_user_dir`（低-中）：只读查用户/权限，返回前脱敏
- `check_service_health`（低-中）：调内部探针
- `grant_db_readonly`（高）：**演示道具**，仅写入本地演示系统，需审批 + 幂等
- `reset_password`（高）：模拟密码重置，需审批
- `notify_user`（中）：经审批后调用通知网关（Demo 中写日志）

### 3.5 记忆五分层（与笔记完全对应）

| 层                                                            | 载体                           | 说明                  |
| ------------------------------------------------------------ | ---------------------------- | ------------------- |
| Session                                                      | SQLite `sessions` + 运行态      | 本次会话发生过什么           |
| Task State                                                   | SQLite `tickets` 状态字段        | 任务执行到哪              |
| Memory                                                       | `memory/long_term/` + SQLite | 跨任务稳定经验（如"该租户偏好中文"） |
| Artifact                                                     | `artifacts/`                 | 计划/文件/报告/代码         |
| Trace                                                        | `traces/*.jsonl` + SQLite    | 系统实际执行了什么           |
| 任务结束：Task State 归档 → `archived`；Session 当轮用完即弃（保留必要摘要进任务状态）。 | <br />                       | <br />              |

### 3.6 三套预算（`budget.py`）

| 预算                                                                                    | 默认值      | 行为                        |
| ------------------------------------------------------------------------------------- | -------- | ------------------------- |
| 步数                                                                                    | 25 步     | 触顶 → `budget_exceeded` 停止 |
| Token                                                                                 | 每任务 200k | 触顶 → 压缩/停止                |
| 时间                                                                                    | 600s     | 触顶 → 终止并通知                |
| 每步执行前 `budget.consume(step, tokens)`，触顶即中断 LOOP，事件进 SSE + Trace，工单转 `failed(budget)`。 | <br />   | <br />                    |

### 3.7 模型路由与 LLM 双引擎

```python
# config: model.provider = "openai" | "ollama"
class llm_gateway:
    def openai(prompt):  # openai, base_url 可配（可指向 OpenAI 也可指向兼容网关）
    def ollama(prompt):  # ollama 本地, 兼容 /v1/chat/completions
```

`model_router` 规则：

- 意图=知识查询 → 轻量快速模型（ollama 可设 `qwen2.5:7b`）
- 意图=高复杂度多 Agent（变更/故障） → 强模型（openai 可设 `gpt-4o`）
- 路由依据：规则 + 可选模型复评，写入 Trace（模型版本可审计）

### 3.8 异常与停止条件（`guards.py`）

- 重复动作检测：同一工具 + 同一参数 + 时间窗内 → 拦截并提示
- 重试策略：指数退避，最大 3 次；3 次失败 → 转人工
- 停止条件：`done:true`（结构化输出）+ 规则校验器（产物完整性）+ 预算
- 关键节点：高风险执行前必须人工确认

### 6.2 LLM 双引擎实现要点

```python
    def __init__(self, provider, model, base_url, api_key):
        self.provider = provider  # "openai" | "ollama"
    def chat(self, messages, **kw):
        if self.provider == "openai":
            from openai import OpenAI
            client = OpenAI(api_key=..., base_url=...)
        else:  # ollama：用 httpx 调 http://localhost:11434/v1/chat/completions
            ...
        return response  # 统一返回 {content, usage, model, latency}
```

两条后端都走 `POST /v1/chat/completions` 协议，Ollama 2.3+ 原生兼容 OpenAI SDK，可把 `base_url` 切到 `http://127.0.0.1:11434/v1` 与 `api_key=ollama`，这样连 `openai` 路径也可以直接对 Ollama 用同一套代码。文档中给两种配置示例 `.env`。

### 6.3 上下文装配算法（核心面试讲点）

```python
def assemble_context(ticket, history, memo, tools_allowed, budget, risk):
    # 结构化、顺序固定，防"自我污染"
    s = [
        ("goal",      ticket.goal),                    # 原始目标
        ("state",     ticket.status),                  # 当前状态
        ("history",   compress(history, max=8)),        # 选：近N条；压：长观测摘要
        ("memo",      memo.relevant(ticket)),           # 记忆：按需
        ("artifacts", latest_artifacts(3)),             # 截：只带最新关键
        ("tools",     tools_allowed),                   # 动态分配
        ("constraints", build_constraints(actor,risk)), # 约束
        ("budget",    budget.left()),
    ]
    return "\n".join(f"<{k}>{v}</{k}>" for k, v in s)
```

- 压：>1000 字符的 observation 先 `summarize`（可配模型），2000 行日志 → 3 行结论
- 截：历史超过阈值 → Auto-Compact 成一段摘要，保留关键状态
- 选：只带"这一圈真正需要"的工具与最近产物

### 6.4 MCP-Style 工具注册与执行

```python
@register_tool(name="grant_db_readonly", risk="high", roles=["operator","admin"])
def grant_db_readonly(params, ctx):
    grant_type = params["type"]; principal = params["principal"]
    if not grant_type in WHITELIST: raise ParamError(...)   # 白名单
    if ctx.approval_required(params):                        # HITL
        return ApprovalRequest(id=approval.create(...))
    result = replace_placeholder_into_demo_db(...)           # 幂等键
    return mask(result)                                      # 脱敏
```

`registry` 两层过滤：按 `roles` 装配进上下文；按 `risk` 决定是否进 HITL。

### 6.5 HITL 中断与恢复

- Agent 请求高风险工具 → orchestrator 生成 `approvals` 行 + 事件 `hitl`，进入 `awaiting_approval`（保留上下文快照）
- 审批通过 → 从快照恢复 LOOP，携带 `approval_id` 参数继续执行
- 驳回 → 工单 `cancelled` 或 `gathering`（改方案）

### 6.6 幂等键与补偿

- 每个高风险工具调用生成 `idempotency_key = ticket_id + ':' + tool + ':' + fingerprint(params)`
- 执行前查历史：已成功 → 直接返回上次结果；进行中（`running`）→ 拒绝
- 失败：状态机标记 failed + 补偿动作（如"回收已授予的权限"）写入 trace

### 6.7 Trace 记录全字段

每次模型调用与工具调用写一条 trace：`req_id, model, prompt_version, context_source, tool_name, params, result, state_before, state_after, latency_ms, tokens, retries`。前端由 Next.js 的 `TraceTimeline` 组件渲染时间线（实时 SSE 推送）。

### 6.8 提示词版本管理

`prompts/` 下每个 `V{v}.md` 登记版本号与内容 hash；每次调用把 `prompt_version` 写进 trace；更新提示词 = 加新版本，可回溯"结果变化来自哪版提示词"。

### 8.3 Docker Compose（示意）

```yaml
services:
  app:
    build: .
    env_file: .env
    volumes: ["./data:/app/data"]
    ports: ["8000:8000"]          # 内部服务，仅 Nginx 可达
  web:                           # 前端 Next.js（App Router）
    build:
      context: ./web
      args:
        NEXT_PUBLIC_API_URL: http://app:8000/api   # 构建期注入（见下方说明）
    environment:
      - NEXT_PUBLIC_API_URL=http://app:8000/api
    depends_on:
      - app
    ports: ["3000:3000"]         # 内部服务，仅 Nginx 可达
  nginx:
    image: nginx:alpine
    volumes: ["./nginx.conf:/etc/nginx/conf.d/default.conf:ro"]
    ports: ["80:80","443:443"]   # 对外唯一入口
    depends_on:
      - app
      - web
  ollama:      # 可选
    image: ollama/ollama
    volumes: ["./ollama:/root/.ollama"]
    ports: ["11434:11434"]       # 仅 Ollama 需要（模型走本地时）
```

**前端** **`web`** **服务衔接说明**

- `web` 目录含独立 `Dockerfile`（基础 `node:20-alpine`，执行 `next build` 生成 `standalone` 产物，`CMD node server.js`）与独立 `.env.production`
- 前端不在浏览器里直接调 FastAPI：对外只暴露 Nginx 一个入口，Nginx 统一反代（`/` → `web:3000`，`/api` → `app:8000`），避免跨域、避免暴露后端端口
- `NEXT_PUBLIC_API_URL` 是**构建期**环境变量（Next.js 会把它内联进客户端包）；由于它只在 Docker 内网使用，值为 `http://app:8000/api` 即可。若前端需在网络侧单独调用后端，则改为该 ECS 的公网地址
- SSE 事件流走同一个 `/api` 反代（`Nginx → app:8000`），前端 `lib/api.ts` 直接 `fetch` 同源即可
